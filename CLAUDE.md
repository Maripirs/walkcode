# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Walkcode is a **no-build, mobile-first** web app for guided coding walkthroughs and quick code drills (NeetCode-style problems). The frontend is vanilla ES modules loaded directly by the browser — no bundler or framework. Since M5 it is served by a small **Node backend** (`server/`) that also exposes a read-only **content API** backed by **Postgres**; the frontend fetches content from `/api/content` and falls back to the bundled `src/data/**` when offline. Since M9 the server also proxies an **optional** AI feedback route (`POST /api/algorithm-feedback`) — see `server/llm.js`; it's off unless an LLM key is configured and degrades to the deterministic checker. The only backend dependency is `pg` (the LLM proxy uses built-in `fetch`). Deployed as one container on Cloud Run; local dev is `docker compose up` (app + Postgres). See `plan.md` for the hosting/backend roadmap.

## Commands

- **Run locally (full stack):** `docker compose up` → app at `http://localhost:8088`, `/api/content` served from a local Postgres. The app auto-seeds Postgres on boot; after editing `src/data/**`, `docker compose restart app` to re-seed. `docker compose down -v` drops the DB volume.
- **Preview frontend only (no API):** serve the repo root with any static server and open `index.html` (ES module imports need HTTP, not `file://`). With no `/api/content`, the app boots from the bundled offline fallback.
- **Ops / hardening (M8):** nightly `pg_dump`→GCS backups (VM cron, 30-day retention) + a **$5 budget wired to a hard billing kill-switch** (Gen2 Cloud Function `ops/killswitch/` disables project billing at the cap). Recovery procedures — backup verify, restore, VM rebuild, and **re-enabling billing after the kill-switch fires** — are in `docs/RUNBOOK.md`. The backup script is `server/scripts/pg-backup.sh` (installed at `/opt/walkcode/pg-backup.sh` on the VM).
- **Syntax check (the only "test" available):** `node --check <file.js>` per source file. Check all of `src/` and `server/` before handing off, e.g. `find src server -name '*.js' -exec node --check {} \;`.
- **Validate drill content:** `node server/scripts/validate-content.mjs` — runs against the assembled bundle and enforces the whole-line drill contract (one blank, `correct` ∈ `choices`, unique choices, feedback for every wrong line, no visible copy of the correct line). Run it after editing any drill/lesson data.
- **Deploy:** build the container and deploy to **Cloud Run** (`walkcode` service, `us-central1`), which reads `DATABASE_URL` from Secret Manager and reaches the e2-micro Postgres over the private VPC path. A new revision auto-seeds/re-mirrors content when the bundled content hash changes. Custom domain `walkcode.maripi.net` (root `CNAME`) is served via the Cloud Run domain mapping. Deploy only when ready to publish. To enable M9's AI coach in prod, store the LLM key (`GROQ_API_KEY` preferred, or `NVIDIA_API_KEY`) as a secret and wire it, e.g. `--set-secrets=GROQ_API_KEY=GROQ_API_KEY:latest` (leave unset to keep the feature off — the app is unaffected).

## Architecture

Pure render-on-state-change loop with no framework. The single source of truth is a mutable `appState` object; every view is a function returning an HTML string that `app.js` writes into `#app`, then re-binds event listeners.

- **`src/app.js`** — the only coordinator. On startup it `await`s `loadContent()` (see below), calls `initContent(bundle)`, then renders. Owns `render()` (a switch on `appState.screen`: `home` | `library` | `drill` | `lesson`), navigation, random-walkthrough history, and drill-queue setup. Wires views to data and re-binds listeners on every render. It also syncs `window.history` so the browser Back/Forward buttons work: `render()` calls `syncHistory()`, and a `popstate` handler restores the view — the push/replace decision and the stored snapshot are the pure helpers in **`src/lib/navigation.js`** (each screen and each opened problem is one history entry; stepping within a lesson updates the entry in place rather than adding one). **Do not add lesson/drill content here.**
- **`src/lib/state.js`** — `appState` (in-memory UI state) plus device-local progress persisted in `localStorage`: `walkcode-states` = per-card `Unseen`/`Seen`/`Solved`; `walkcode-drills` = solved-drill ids (M10, keyed by the stable `drill.id` from `assemble.js`; `isDrillSolved`/`markDrillSolved`/`drillSolvedCount`); `walkcode-language` = JS/Python. No server persistence. The shared `includeCompleted` flag drives whether *random* drills **and** random walkthroughs skip already-completed items.
- **`src/lib/ui.js`** — shared render helpers (`shuffle`, `languagePicker`, `difficultyTag`, `feedback`, `topBar`). `shuffle` is what keeps answer position out of the answer key.
- **`src/lib/problem-source.js`** — derives each problem's LeetCode URL from its title; add a slug to `leetCodeSlugOverrides` when a title doesn't map cleanly.
- **`src/views/`** — one file per screen (`home`, `library`, `drill`, `drill-picker`, `lesson`), each returning markup and (for interactive screens) exporting a `bind*` function for its listeners. On **home**, both mode cards show a **`<solved>/<total> done`** progress tally and **expand in place** (no separate screen; one open at a time) into a **Random** option (with the shared include-completed toggle) vs a **Pick/browse** option: **Code drills** → Random reps vs Pick-or-filter (→ the **`drill-picker`** screen: a filterable list of drills by type + difficulty + done state); **Full walkthroughs** → Random walkthrough vs Pick-a-problem (→ the **`library`** screen, now purely the easier→harder browse list). The `.mode-expand` panel animates **open and closed** (the closing panel is animated out before `app.js` re-renders, since innerHTML replacement has no exit animation; a one-shot `state.animateCard` gates the open animation so re-renders while open — e.g. the checkbox — don't replay it), respecting `prefers-reduced-motion`.

### The data layer is the product

Content is authored in `src/data/` and assembled by **`src/data/assemble.js`** — the key file to read first. `assembleBundle()` merges the fragments below into a single bundle (`cards`, per-language `lessons`, `drillItems`) plus a content-hash `version`. That bundle is the one shape used three ways: the seed importer writes it to Postgres, the server rebuilds it from the DB for `/api/content`, and it is the browser's **offline fallback** — so DB, API, and fallback can't drift.

- **`src/data/model.js`** — thin selector over the loaded bundle. `initContent(bundle)` populates it; `cards`, `cardsById`, `difficultyFor`, `isBuilt`, `lessonFor(card, language)`, `orderedCards()` (the library browse order — a flat easier→harder list, not grouped by topic so the category doesn't spoil the Recognize step), `drillItems()` read from it. Views consume the same interface as before. Each assembled lesson also carries `intuition` (a problem-specific "aha" shown on the Understand step; authored lessons only), optional `examples` (extra worked cases beyond the single `inputOutput` example) and `description` (a fuller problem statement) — both enrichment, **not** part of `isComplete` — and two flags: `isComplete` (all authored fields present — derived) and `isBuilt` (complete **and** certified → shown to learners).
- **`src/lib/content-loader.js`** — `loadContent()`: fetch `/api/content` → cache in `localStorage` → on failure use the cache → finally the bundled `assembleBundle()`.
- **`server/db.js`** — schema, `ensureSeeded()` (auto-migrate + seed when the DB is empty or the content hash changed), and `getContentBundle()` (rebuilds the client bundle from Postgres).
- **`server/llm.js`** (M9) — provider-agnostic (OpenAI-compatible `/chat/completions`) proxy for a **Socratic "build the algorithm" coach**. `algorithmCoachTurn()` is one turn: given the problem reference (kept private — the intended-approach steps AND the reference solution code, so the model knows the exact loop/update/stop conditions), the steps accepted so far, the current question, and the learner's answer, it returns `{decision: accept|revise, acceptedStep, feedback, nextPrompt, done, summary}` — accepting a concise step into the growing solution or nudging without revealing the answer. The system prompt gives the model a structural checklist (state/setup → loop → per-iteration update → stopping condition → return) so it teaches loop mechanics and has a well-defined completion point. Config via env — the provider **auto-selects** from whichever key is set (`GROQ_API_KEY` → Groq, default model `llama-3.3-70b-versatile`; else `NVIDIA_API_KEY`/`LLM_API_KEY` → NVIDIA NIM, default `meta/llama-3.1-8b-instruct`; none → `llmEnabled()` false and the route 503s). `LLM_BASE_URL`/`LLM_MODEL` override the endpoint/model. **Groq's free-tier Llama-70B is the current local default** — dramatically better judgment/coverage than NVIDIA's 8B (the only fast+free NVIDIA option; its 70B models were 404/unavailable and its 49B ~34s/turn) — at the cost of a 12k-tokens/minute free limit (fine for one human, but bursts of testing 429). Server-side guards compensate for the small model: near-duplicate step dedup, a completion backstop (finish once the solution reaches the reference-algorithm length, or when it's over that length and churning), stripping question sentences out of `feedback`, and a learner-controlled "finish" control. **Note: `docker compose restart` does NOT re-read `.env`; changing `LLM_MODEL` needs `docker compose up -d` (recreate), or just rely on this code default.** The key never reaches the browser. `server/server.js` adds the rate-limited `POST /api/algorithm-feedback` route and advertises the capability via `/api/health` → `features.algorithmFeedback`. When on, the coach **replaces** the drag-and-drop builder on the Algorithm step; the builder is the offline/no-key fallback. **The model's response is untrusted — the client escapes it before rendering.**
- **`curriculum.js`** — the roadmap: topic → problem-title lists. Defines which cards exist.
- **`lesson-records.js`** — explanations, `featured` full lesson records, concept choices, briefs, complexity lessons, per-topic `profiles`/`fallback`.
- **`walkthrough-upgrades.js`** — full lesson records for roadmap problems upgraded from WIP to Built (JS + Python code, steps, fixes, complexity).
- **`examples.js`** — per-title `examplesByTitle` (extra worked examples: `{input, output, note?}`, rendered in the Understand step's collapsible "More examples") and `descriptionsByTitle` (an optional fuller problem statement). Authored records in `lesson-records.js`/`walkthrough-upgrades.js` can override via inline `examples`/`description`.
- **`prediction-drills.js`** (M10) — `predictionDrills` per title: behavior-prediction drills (`type: 'predict'`) — a self-contained function + a call, choices are candidate return values. JS + Python variants.
- **`debug-drills.js`** (M10) — `debugDrills` per title: two-step debugging drills (`type: 'debug'`) — a function with one wrong line; the learner spots the bug line, then picks the fix. Structured spec (JS + Python line text + shared feedback); `assemble.js` flattens it per language.
- **`edge-case-drills.js`** (M10) — `edgeCaseDrills` per title: edge-case drills (`type: 'edge-case'`) — a function + "which input yields this result?"; `choices` are input literals (shared across languages), `correct` yields `target`. Only the function `code`/`call` differ per language.
- **`drills.js`** — code-fix exercises (`codeExercises`), standalone `extraCodeDrills`, `drillContext`, `drillDifficultyByTitle`.
- **`supplemental-drills.js`** + **`supplemental-solutions.js`** — extra standalone drills and their full JS/Python reference solutions; each drill blanks one real line of its solution (`blank(fullCode, correctLine)`).
- **`languages.js`** — Python variants (`pythonSolutions`, `pythonExercises`) keyed by title / `title:index`.
- **`difficulty.js`** — Easy/Hard title overrides; **Medium is the fallback**.

**A problem is "Built" (shown to learners) only when it is BOTH content-complete AND certified.** _Complete_ is **derived** in `assemble.js` (`isComplete()`: has intuition, exercises, complexityGuide, inputOutput, conceptChoices) — author the content and it's complete. _Certified_ is a **human review gate**: the `certifiedTitles` Set in `assemble.js` (add a title to publish it). `isBuilt = isComplete && certified`. This keeps newly-authored problems out of the live library until reviewed. Incomplete problems show a WIP banner; complete-but-uncertified ones are hidden from the public but visible to the owner in **review mode** (`?review=1`, persisted) as a "Pending review" band they can run. Random walkthroughs pick certified problems only. `node server/scripts/validate-content.mjs` fails if a certified problem is incomplete and lists pending-review problems.

## Content conventions (from CONTRIBUTING.md)

- A problem earns **Built** only when all five lesson stages are concrete and interactive: **Recognize → Algorithm → Code fixes → Complexity → Review**. Don't badge generic/draft content as Built or remove the WIP signal early.
- Adding/upgrading a problem touches multiple data files in step: title in `curriculum.js`, explanation + full record + concept choices + input/output in `lesson-records.js` (or a record in `walkthrough-upgrades.js`), exercises in `drills.js`, Python variants in `languages.js`, difficulty classification. Keep each kind of content in its matching file.
- **Concept-choice lists: the first element is the answer key**; the UI randomizes display order via `shuffle`. Never encode the answer as a position.
- **Recognize step leads with comprehension, then tests recognition:** the panel shows the full plain-language problem statement (`explanation`/`brief`, plus the optional fuller `description`) first, then Input/Output/Example and a collapsible **"More examples"** (`examples`), then the **concept check**. Extra examples sit before the check (they don't name the pattern); the intuition/notice do, so they stay hidden. Because the check is a *recognition* exercise, the problem-specific `intuition` callout (authored Built lessons only) and the "what to notice" cues (`concepts`) — which name the pattern — are **hidden until the learner answers the check**, then revealed as the explanation (`data-recognition-reveal` in `views/lesson.js`). Don't move `intuition`/`concepts` back above the check; they give the answer away. There is no generic hint — omit rather than pad.
- **The Algorithm step's drag-drop builder is now a pure ordering task** (the offline/no-key fallback; the M9 AI coach replaces it when a key is configured). `ensureAlgorithmState` puts all the real `algorithm` steps into the answer, shuffled, and the learner drags them into order — there is no "available" bank, no add/remove, and **no `distractors`** (that field was removed everywhere). Reordering is pointer-based (`enableStepSorting`), so it works on touch.
- **User-facing content is escaped on render.** Since the DB is a supported authoring path (M5), all interpolated prose passes through `escapeText`/`richText` (or `escapeCode` for code blocks) from `ui.js`. Keep new content interpolations escaped — don't reintroduce raw `${...}` of authored text.
- **Lesson navigation is a guided stepper:** one tappable progress rail (the "move through the steps" axis) + one always-present Back/Next-step bottom bar; "go to another problem" is a separate footer axis. Tab labels (`Understand`/`Algorithm`/`Code`/`Complexity`/`Review`) with friendly per-step headers. Don't reintroduce a third competing nav control.
- **Drills are typed (M10); `fill-blank` is the default.** A drill's `type` selects how it renders and validates (`views/drill.js` switches on it; `type` absent ⇒ `fill-blank`, so legacy drills are unchanged). The queue is shuffled, so types **interleave**. Types:
  - **`fill-blank`** — the exercise `code` is the full solution with one line blanked (`___`), and `choices` are complete candidate lines (one equals `correct`) — never single tokens. The correct line must be **unique** in the shown solution (no leak). Correct feedback (`why`) explains; per-wrong-line feedback (`wrong`) must not reveal the answer.
  - **`predict`** — a complete function + a call (`input`); `choices` are candidate return values. Authored in `prediction-drills.js`.
  - **`debug`** — a two-step drill: a function with one wrong line; the learner picks the buggy line, then the fix. Authored in `debug-drills.js`.
  - **`edge-case`** — a function + "which input produces this result?"; `choices` are input literals, `correct` is the one yielding `target`. Authored in `edge-case-drills.js`.
  - **The validator EXECUTES the JS variant** of predict/debug/edge-case (`validate-content.mjs`): predict code is run against its call and must equal `correct`; debug runs the buggy code (must differ) and the fixed code (buggy line swapped for the fix — must equal `correctReturns`); edge-case runs `call(choice)` for every choice and requires only the correct one to hit `target`. So a wrong answer, non-manifesting bug, or non-unique edge case can't ship. Python variants mirror the JS and are structurally checked.
- Keep every JS/Python drill solution **≤ 36 lines** (`MAX_DRILL_CONTEXT_LINES` in `views/drill.js`); the full solution stays visible below the prompt with the blanked line highlighted.
- Keep the app lightweight and mobile-first; **add no dependencies or build step**. Update `CONTRIBUTING.md` in the same change whenever a content schema or user workflow changes.
